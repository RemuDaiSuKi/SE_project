**A. 使用者、登入與視窗**
1. 兩種使用者：老師與學生。老師以密碼登入，密碼只從環境變數讀取，未設定時伺服器拒絕啟動。
2. 學生不需帳號：老師建立活動時輸入組數與組名（不寫死），系統為每組產生 6 碼、不易猜的組別代碼，只顯示給老師；老師在課堂上私下發給各組。學生輸入代碼即加入該組，系統不區分組內個人；同組可多人同時加入，同組所有視窗同步看到該組的送出與結果。
3. 系統只在單一電腦上運作，以多個瀏覽器視窗模擬老師與各組學生，不需支援其他設備連線。每個視窗身分獨立：同一瀏覽器的不同視窗可分別是老師與不同組別，互不覆蓋。
4. 輸入錯誤代碼時拒絕且不透露任何組別資訊；同一視窗連續輸錯過多次就暫時鎖定（次數與時間可設定），限制以視窗為單位，不可封鎖整台電腦而影響其他組。老師可重新產生某組代碼，舊代碼與用舊代碼加入的連線立即失效。

**B. 學習單匯入**
5. 老師從 Google Sheets「檔案 → 下載 → .xlsx」後上傳系統；系統不連 Google 帳號。
6. 必須動態解析，不可依賴特定檔名、工作表名、儲存格位置或題數（助教會用另一份學習單測試）：
   - 在每個工作表找「同一列同時出現『題號』『題目』『作答』」的表頭列（標籤文字可設定），各欄位範圍以表頭儲存格（含合併範圍）涵蓋的欄為準。
   - 表頭以下、「題目」欄範圍內有文字的列為「題目列」；空白分隔列一律忽略。
   - 題目列在「作答」欄範圍內的空白儲存格就是「填空格」；合併儲存格視為一格、以左上角代表；只有空白字元也算空白。每個題目列恰好一個填空格。
7. 依「工作表順序 → 由上而下」編系統題號 1..N，題數必須等於題目列數。不匯入、不保存題目敘述，題目只以題號表示。
8. 題組：「題號」欄的儲存格向下合併、跨越兩個以上題目列時，這些列構成一個題組；作答欄範圍內的非空白文字（如「（1）」「（2）」）是子題標籤，不是填空格。需記錄每題的學習單原始題號、子題標籤、填空格位置（工作表＋儲存格）與所屬題組。
9. 匯入後先顯示確認畫面：題數、題組數，以及每題的系統題號、原始題號、子題標籤、填空格位置、所屬題組；老師按確認才建立題目，按取消則不建立任何東西、可重新選檔。
10. 以下情況一律拒絕、不部分匯入，並以繁體中文說明原因與位置（工作表＋列或儲存格）：非試算表或檔案損毀、空檔、找不到表頭、找不到任何題目列、某題目列有 0 個或 2 個以上填空格（例如老師已預先填答案）、題組合併範圍內有非題目列、超過檔案大小或題數上限（預設 10 MB、500 題，可設定）。多個工作表時只處理有表頭的工作表，題號跨工作表連續編號。

**C. 搶答活動**
11. 老師用一份已確認的學習單建立活動；同時只能有一場「準備中」或「搶答中」的活動，同一份學習單可先後辦多場。
12. 活動階段單向前進：準備中 → 搶答中 → 已結束，只有老師能切換；已結束不能重新開始；未綁定已確認學習單不能開始。階段變更須在 2 秒內同步到所有已連線視窗；新連線或斷線重連時立即取得目前階段與自己組的紀錄。
13. 搶答中所有搶答單位同時開放，各組自行選題，直到結束都不關閉個別單位。搶答單位 = 不屬於題組的單一題目，或一整個題組。題組必須一次送出全部子題答案，缺任一題就拒絕整筆並列出缺少的題號；題組的成功、順位、成功數都以整個題組為一個單位。
14. 只有「搶答中」能送出。每組對每個搶答單位只能送出一次（同組任一成員送出後，該組對該單位就鎖定）。答案去除前後空白後不可為空，長度上限預設 200 字（可設定）；題號必須存在且屬於本活動。
15. 判定只依伺服器處理順序，忽略客戶端提供的任何時間或結果。每個單位依處理順序給不重複順位 1, 2, 3…；第一筆合法送出為「搶答成功」，之後的送出仍記錄並給順位。多組同時送出時必須恰好一組成功、順位不重複不遺漏。送出後立即告知該組「搶答成功」或「未搶到（第 N 順位）」。老師按結束的同時有人送出，以伺服器先處理者為準。
16. 系統不判斷答案對錯（學習單沒有標準答案），「成功」只代表最先送出。
17. 畫面上只顯示題號標示，例如「第 5 題（學習單第 3 題）」或「題組 1：第 1、2 題（學習單第 1 題（1）（2））」，學生對照手上的紙本學習單作答。
18. 隔離：結束前學生只看得到自己組的送出紀錄與結果，看不到他組的答案、送出狀態、順位，也看不到哪些題目已被搶走（因此可能對已被搶走的題送出而得到「未搶到」，這是預期結果）。此限制必須由伺服器保證，學生直接要求他組或全體資料一律拒絕。
19. 老師在搶答中可即時看到每個單位的所有送出（組別、答案、順位、是否成功）、各組成功數與冷卻狀態；結束後看完整結果。學生在結束後可看到每個單位的成功組別與成功答案，以及各組成功數。到結束都沒人送出的單位標示「無人搶答」。
20. 老師判定無效（搶答中或結束後皆可）：把成功送出標為無效但保留原順位，依順位由下一筆遞補為成功；沒有可遞補者時，搶答中該單位重新開放（被判無效的組仍不能再送），已結束則標示「無人搶答」。立即重算各組成功數，並通知被判無效與遞補成功的組，通知不洩漏他組答案。同一單位可連續判定無效多次。
21. 公平機制（冷卻）：某組「即時送出」搶答成功時，若「該組成功數 − 全體組別最少成功數 ≥ K」，該組從判定成功時起冷卻 N 秒（預設 N=10、K=2，可設定、可停用，建立活動時老師可覆寫）。成功數以搶答單位計（一個題組算 1）。冷卻中送出會被拒絕並告知剩餘秒數，該次嘗試不佔順位、也不算用掉對該單位的唯一一次。遞補成功不觸發冷卻；若被判無效的那次成功正好造成冷卻，冷卻立即解除。只有 1 組時永遠不會冷卻。學生看得到自己組的冷卻與倒數，老師看得到所有組。冷卻以伺服器時鐘計算。
22. 保存與重啟：進行中的狀態只放記憶體；按下結束時把完整結果（所有送出、順位、成功與無效、各組成功數）寫入持久儲存，寫入成功後才通知「已結束」；結束後的判定無效也要立即保存。伺服器重啟時，未結束（準備中、搶答中）的活動標為「已中斷」並作廢，組別代碼失效，使用者重連時看到「活動已中斷，請老師重新建立」；已結束活動的結果在重啟後完整可讀。

**D. 答案寫回與結果匯出**
23. 寫回：老師選一場已結束的活動，系統把每題成功組別的答案寫入原學習單對應的填空格，產生一份新的 .xlsx 供下載（原上傳檔不動），可再匯入 Google Sheets。除填空格外，其他儲存格內容、合併範圍、工作表結構、格式與子題標籤都不能被改動。沒有成功答案的題目保持空白，並在完成訊息列出題號。寫回只依伺服器判定的結果；寫回前驗證學習單結構與匯入時一致，不一致就拒絕並說明。
24. CSV 匯出：5 欄「題號,組別,答案,搶答順位,結果」，題號為系統題號，結果為「成功」「未搶到」「無效」之一（被判無效的紀錄保留原順位）；依題號遞增、同題內依順位遞增排序；題組的一筆送出依每個子題各輸出一列，組別與順位相同。使用 UTF-8 含 BOM，正確處理含逗號、引號、換行的答案；沒有任何紀錄時只輸出標題列並提示。

**E. 權限、錯誤與機敏資料**
25. 只有老師能匯入、確認題目、建立活動、切換階段、判定無效、重新產生代碼、寫回與匯出；學生或未登入者的請求一律拒絕並回應無權限。
26. 所有 UI 文字與錯誤訊息使用繁體中文，不顯示堆疊追蹤或內部錯誤細節，不洩漏他組資料或機敏資料。
27. 密碼、Token、組別代碼不可出現在程式碼、文件、測試資料、log 或 repo 中；.env 列入 .gitignore，另提供只含佔位值的 .env.example。
28. 所有參數（檔案與題數上限、表頭標籤、答案長度、N、K、輸錯限制、組數上限、資料目錄、port）皆可設定、不寫死；伺服器只監聽 127.0.0.1。

## 3. 探索時定下的預設

以下是規則沒講到、探索時採用的預設，寫 spec 時請標註「預設」。標 ★ 的項目要和 SpecKit 組對齊（見第 7 節）。

### 活動與組別

- **組數與組名：** 組數 1–20，上限可設定。組名去除前後空白後為 1–20 字，同一活動內不可重複。
- **組別代碼：**
  - 6 碼，字元集為 `23456789ABCDEFGHJKMNPQRSTUVWXYZ`，共 31 個字元，已排除容易混淆的字，約有 8.9 億種組合。
  - 用 `secrets` 產生，在所有有效代碼中保證唯一。
  - 輸入時不分大小寫。
- **輸錯鎖定：**
  - 輸錯 5 次鎖定 60 秒，沿用 `BUZZER_LOCKOUT_*` 設定與 `WindowRegistry`。
  - 成功一次就歸零。
  - 鎖定期間連正確代碼也拒絕，並提示剩餘秒數。
- **★ 階段不可跳躍：** 準備中必須先經過搶答中，才能到已結束。
- **準備中的學生畫面：** 看得到搶答單位清單，但送出按鈕停用。
- **★ 準備中無法取消（G3）：** 不新增「取消」狀態。建錯活動時，只能「開始 → 立即結束」，留下一場空結果。
- **G2 綁定學習單：** 建立活動時就必須綁定已確認的學習單。開始時仍再檢查一次，當作伺服器端的防禦性不變式。
- **重新產生代碼：**
  - 只在準備中與搶答中可用。
  - 被踢出的視窗顯示「組別代碼已更新，請向老師索取新代碼」。
  - 該組的紀錄與冷卻狀態不受影響。
- **★ 已結束活動的代碼（G5）：** 以雜湊保存，重啟後仍可用來加入，並唯讀檢視結果。由此推論：明文代碼不寫入磁碟，所以重啟後老師畫面無法再顯示已結束活動的代碼。
- **G4 入庫時機：** 活動與組別的基本資料（含代碼雜湊）在建立時就寫入 SQLite，這樣重啟時才能把活動標為「已中斷」。送出等進行中狀態仍只放記憶體。
- **重啟：** 啟動時把「準備中」「搶答中」的活動改為「已中斷」。已中斷的活動在老師的歷史清單中看得到，但不能寫回或匯出。
- **重連訊息：** 學生視窗保存 `{token, activityId}`。重連時：
  - Token 已失效、而活動是「已中斷」：顯示「活動已中斷，請老師重新建立」。
  - 其他情況：顯示「連線已失效，請重新輸入代碼」。

### 送出與判定

- **答案內容：**
  - 保存去除前後空白後的值。
  - 長度以 Unicode 字元（code point）計算。
  - 允許換行，拒絕其他控制字元。
- **不合法的送出不留紀錄：** 空白、超長、題組缺漏、冷卻中、非搶答中的送出，都不留紀錄、不佔順位，也不算用掉機會。
- 客戶端附帶的時間或結果欄位一律忽略。
- **G9 序列化與結束保存：**
  - 伺服器以單一 worker 執行（`workers=1` 已固定），所有狀態變更都經過同一把鎖序列化。
  - 結束時的保存也在鎖內完成。保存失敗時維持「搶答中」，老師看到「結果保存失敗，請重試」，不廣播「已結束」。
- **G14 只送出題組裡的單一子題：** 視同題組缺漏，列出缺少的題號。
- **判定無效的範圍：** 只有「成功」的紀錄可以判定無效，也不提供復原。
- **G8 重新開放後的送出：** 判定無效讓單位重新開放後，下一筆新送出算「即時送出」，要做冷卻檢查。
- **★ G7 冷卻公式：**
  - 判定成功後再計算，「該組成功數」包含這次成功，「全體最少成功數」也把自己算進去。
  - N 的範圍是 1–300 秒，K ≥ 1，另有獨立的啟用開關。
  - 建立活動時老師可以覆寫這些值。
- **判定無效不回溯冷卻：** 判定無效改變了全體最少成功數時，不會回溯對其他組觸發冷卻，也不會因此解除其他組的冷卻。
- **結束後的學生畫面：**
  - 看得到每個單位的成功組與成功答案、各組成功數，以及自己組的全部紀錄（含被判無效的紀錄）。
  - 看不到他組未成功的答案。

### 顯示

- **單位標示：** 依規則 17 的格式。
- **★ G12 多工作表：** 有兩個以上題目工作表時，原始題號可能重複，所以標示中要加上工作表名。

### 安全

- **G15 Token 與代碼的傳送方式：**
  - WebSocket 的 Token 放在連線後的第一則訊息，不放在網址 query，因為 query 會進 access log。
  - 組別代碼放在 POST body。
  - uvicorn 的 access log 已經關閉。
- **WebSocket 來源檢查：**
  - Host 標頭檢查已在 `align-teacher-side-with-speckit` 移除（與 SpecKit 組一致），監聽位址改由 `BUZZER_HOST` 設定。
  - 是否另外檢查 WebSocket 的 `Origin`，請先和 SpecKit 組確認（對方目前沒有檢查）。
- **機敏資料：**
  - 代碼與 Token 不能進 log。資料庫只存雜湊。
  - 測試用的代碼在測試執行時產生，不寫在任何檔案裡。
- **G10 已知限制：** 鎖定以視窗為單位，關掉視窗重開就能繞過，這在單機環境無解。真正的防線是代碼的組合數，鎖定只是減速。

## 4. 驗收情境（WHEN / THEN）

以下沿用探索時列出的情境。數值以預設值計算：輸錯 5 次鎖定 60 秒、答案上限 200 字、K=2、N=10。

### 活動與代碼
- **ACT-01** WHEN 建立 3 組的活動　THEN 產生 3 個互不重複的 6 碼代碼，只在老師畫面顯示，活動狀態為「準備中」。
- **ACT-02** WHEN 已有一場準備中或搶答中的活動，又要建立新活動　THEN 拒絕。
- **ACT-03** WHEN 組名重複或空白，或組數超過上限　THEN 拒絕並說明原因。
- **JOIN-01** WHEN 學生輸入正確代碼　THEN 加入該組，畫面顯示組名與目前階段。
- **JOIN-02** WHEN 輸入錯誤代碼　THEN 顯示「代碼無效」，回應的內容與時間都不透露任何組別資訊。
- **JOIN-03** WHEN 視窗 W1 連續輸錯 5 次　THEN：
  - W1 被鎖定 60 秒，期間連正確代碼也拒絕，並顯示剩餘秒數。
  - 同一台電腦的 W2 仍然可以正常加入。
  - 60 秒後 W1 恢復。
- **JOIN-04** WHEN 老師重新產生 A 組的代碼　THEN：
  - 用舊代碼加入的視窗立即被踢出，舊代碼無法再使用。
  - 新代碼可以加入。
  - A 組原有的送出紀錄仍在，其他組不受影響。
- **JOIN-05** WHEN 同一個瀏覽器的視窗 1 登入老師、視窗 2 加入 A 組、視窗 3 加入 B 組，然後重新整理視窗 2　THEN 三個身分互不覆蓋，視窗 2 仍是 A 組。

### 階段與同步
- **PH-01** WHEN 老師按「開始」　THEN 所有已連線的視窗在 2 秒內顯示「搶答中」。
- **PH-02** WHEN 用學生 Token 呼叫切換階段的 API　THEN 回應「無權限」。
- **PH-03** WHEN 對已結束的活動按開始，或想從準備中直接跳到已結束　THEN 拒絕。
- **PH-04** WHEN A 組的視窗在搶答中斷線後重連　THEN 立即取得目前階段、A 組的紀錄，以及冷卻剩餘秒數。
- **PH-05** WHEN 搶答中途有新視窗加入 A 組　THEN 新視窗立即看到 A 組既有的送出與結果。

### 送出
- **SUB-01** WHEN A 組第一個送出第 5 題　THEN A 組看到「搶答成功」。
- **SUB-02** WHEN B 組之後也送出第 5 題　THEN B 組看到「未搶到（第 2 順位）」。
- **SUB-03** WHEN 5 組同時送出同一題（並行測試）　THEN 恰好 1 組成功，順位是 1–5，不重複也不遺漏。
- **SUB-04** WHEN A 組的另一個視窗再送出第 5 題　THEN 以「已送出過」拒絕，不給順位。
- **SUB-05** WHEN 送出只有空白的答案　THEN 拒絕，而且不算用掉機會；之後送出合法答案仍然可以。
- **SUB-06** WHEN 送出 201 字的答案　THEN 拒絕。WHEN 送出剛好 200 字　THEN 接受。
- **SUB-07** WHEN 在準備中或已結束時送出　THEN 拒絕。
- **SUB-08** WHEN 送出不存在的單位，或屬於其他活動的單位　THEN 拒絕。
- **SUB-09** WHEN 送出的請求附帶 `timestamp` 或 `result` 欄位　THEN 這些欄位被忽略，結果完全不受影響。
- **SUB-10** WHEN 老師按結束的同時有學生送出　THEN：
  - 伺服器先處理的送出會被記錄，並出現在結果中。
  - 結束之後才處理的送出，以「活動已結束」拒絕。

### 題組
- **GRP-01** WHEN A 組一次送出題組 1 兩個子題的答案　THEN 產生一筆紀錄、一個順位，成功數 +1。
- **GRP-02** WHEN 題組 1 只填了第 1 題　THEN 整筆拒絕並列出「缺少第 2 題」，不算用掉機會。
- **GRP-03** WHEN 只針對第 1 題（屬於題組 1）單獨送出　THEN 視同題組缺漏處理。

### 隔離與同步
- **ISO-01** WHEN 結束前用學生 Token 呼叫全體送出的 API，或帶入他組的 ID　THEN 回應「無權限」。
- **ISO-02** WHEN B 組搶走了第 5 題　THEN A 組收到的推播與 API 回應中，完全沒有第 5 題的狀態。
- **ISO-03** WHEN A 組在視窗 1 送出　THEN A 組的視窗 2 在 2 秒內看到這筆送出，而且第 5 題變成已鎖定。
- **ISO-04** WHEN 活動已結束　THEN 學生可以取得每個單位的成功組與成功答案，以及各組成功數。

### 監看與結果
- **MON-01** WHEN 搶答中有任何一組送出　THEN 老師畫面在 2 秒內顯示這筆送出的組別、答案、順位與是否成功，並更新各組成功數與冷卻狀態。
- **RES-01** WHEN 活動結束　THEN：
  - 老師看到完整結果。
  - 學生看到第 3 節定義的範圍。
  - 從頭到尾沒人送出的單位標示「無人搶答」。

### 判定無效
- **INV-01** 搶答中、有下一順位：判定 A 組（第 1 順位）無效：
  - B 組（第 2 順位）遞補成功，成功數重算。
  - A 組收到「判定無效」通知，B 組收到「遞補成功」通知，兩則通知都不含他組的答案。
  - 即使 B 組此時符合冷卻條件，也不觸發冷卻。
- **INV-02** 搶答中、沒有下一順位：
  - 單位重新開放。A 組再送出時以「已送出過」拒絕。
  - 之後 C 組送出：得到第 2 順位、成功。這屬於即時送出，要做冷卻檢查。
- **INV-03** 已結束、有下一順位：
  - 判定結果立即保存，重啟後仍然反映遞補後的結果。
  - 寫回與 CSV 都跟著更新。
- **INV-04** 已結束、沒有下一順位：該單位標示「無人搶答」，寫回時保持空白。
- **INV-05** 同一單位連續判定兩次無效：第 1 順位無效 → 第 2 順位成功 → 第 2 順位也判無效 → 第 3 順位成功。
- **INV-06** 被判無效的那次成功，正好是觸發冷卻的那一次：冷卻立即解除，並通知該組。
- **INV-07** 對「未搶到」的紀錄判定無效：拒絕。學生呼叫判定無效的 API：回應「無權限」。
- **INV-08** 判定無效後全體最少成功數改變：不會回溯觸發或解除其他組的冷卻。

### 冷卻（3 組、K=2、N=10）
- **COOL-01** WHEN A 組搶到第 1 題　THEN 1 − 0 = 1，不冷卻。WHEN A 組再搶到第 2 題　THEN 2 − 0 = 2，冷卻 10 秒。
- **COOL-02** WHEN A 組在冷卻中送出第 3 題　THEN 拒絕並告知剩餘秒數，不佔順位。WHEN 冷卻期間 B 組送出第 3 題　THEN B 組拿到第 1 順位。WHEN 冷卻結束後 A 組送出第 3 題　THEN 可以送出，拿到第 2 順位。
- **COOL-03** WHEN 成功數為 A=2、B=1、C=1，A 組又成功一次　THEN 3 − 1 = 2，觸發冷卻。WHEN 成功數為 A=1、B=1、C=0，A 組又成功一次　THEN 2 − 0 = 2，觸發冷卻。
- **COOL-04** WHEN 活動只有 1 組，或冷卻已停用　THEN 永遠不冷卻。
- **COOL-05** WHEN 老師建立活動時覆寫 N=5、K=3　THEN 該場活動依覆寫後的值計算。
- **COOL-06** WHEN 搶到一個題組　THEN 成功數只 +1。
- **COOL-07** WHEN A 組在冷卻中　THEN A 組畫面顯示倒數，老師畫面看到所有組的冷卻狀態，B 組看不到 A 組的冷卻狀態。

### 保存與重啟
- **PER-01** WHEN 老師按結束　THEN 結果完整寫入資料庫後才廣播「已結束」。重啟後老師仍可完整讀取結果、匯出 CSV 與寫回。
- **PER-02** WHEN 搶答中重啟伺服器　THEN：
  - 活動被標為「已中斷」。
  - 學生重連時看到「活動已中斷，請老師重新建立」，舊代碼失效。
  - 老師可以建立新活動。
- **PER-03** WHEN 結束時寫入資料庫失敗（測試中注入錯誤）　THEN 活動維持搶答中，老師看到「結果保存失敗，請重試」，不廣播已結束。
- **PER-04** WHEN 伺服器重啟　THEN 已結束活動的組別代碼仍然可以加入，並唯讀檢視結果（G5 的預設）。

### 與寫回、CSV 串接（端到端）
- **E2E-01** WHEN 用範例 B 建立 3 組活動，各組搶答後結束，再呼叫寫回與 CSV 匯出　THEN：
  - 寫回只寫入成功答案；用 `FakeSheetsGateway.writes` 驗證。
  - CSV、老師畫面、學生畫面的判定結果一致。
- **E2E-02** WHEN 對已中斷或尚未結束的活動呼叫寫回或 CSV 匯出　THEN 以 409 拒絕。

### 權限與安全
- **AUTH-01** WHEN 未登入者或學生 Token 呼叫建立活動、切換階段、判定無效、重新產生代碼、老師監看等 API　THEN 一律回應繁中的「無權限」。
- **SEC-01** WHEN 跑完整套測試後掃描 log 與畫面輸出　THEN 找不到密碼、Token 或組別代碼。

## 5. 現有程式中要接的地方

### 結果契約：`app/results/contract.py`

這是本 change 與寫回、CSV 之間的介面，設計理由見 `openspec/changes/archive/2026-11-22-add-worksheet-import-and-export/design.md` 的 D8。

- **資料結構：**
  - `ActivityResult(activity_id, worksheet_id, ended_at, groups, units)`
  - `ResultGroup(group_id, name)`
  - `ResultUnit(unit_id, question_nos, records)`：`unit_id` 單題為 `"Q<題號>"`，題組為 `"G<題組號>"`
  - `ResultRecord(rank, group_id, answers, invalidated)`：`answers` 是「系統題號 → 答案」
- **核心不變式：** 每個單位中「順位最小、且未被判無效」的那筆就是成功。遞補與重新開放都符合這個式子。老師畫面、學生畫面、推播、寫回、CSV 都必須用 `winner_of`、`outcome_of`、`success_counts`、`winning_answers` 判定，**不要另寫一套判定邏輯**。
- **契約驗證：** `validate_result` 會檢查每個單位的順位從 1 連續編號、答案的題號和單位一致、組別存在。被拒絕的送出（冷卻中、缺漏等）不能佔順位，剛好也符合這個檢查。
- **成功數：** 規則 22 要求保存各組成功數，可以存；但顯示與判定一律用 `success_counts()` 推導，以免兩邊不一致。
- **冷卻記錄：** 契約裡沒有「即時送出／遞補」的欄位。冷卻需要知道是哪一筆成功造成的（INV-06），這屬於本 change 的內部狀態，不需要改契約。
- **要替換的結果來源：**
  - 實作一個以 SQLite 為後端的 `FinalResultSource`，`lookup(activity_id)` 依活動狀態回傳：
    - 找不到活動：`not_found`
    - 準備中、搶答中、已中斷：`not_ended`
    - 已結束：`ended` 加上結果
  - 在 `app/main.py` 的 `create_app` 裡取代預設的 `NoActivitiesSource()`。
  - `app/api/outputs.py` 的寫回與 CSV 端點已經會依這三種狀態回應，不必修改。

### 搶答單位的來源

學習單的解析結果在 `WorksheetStore.get(id).parsed`（`app/worksheet/store.py`、`app/worksheet/model.py`），單位由它推導：

- **單題：** `group_no is None` 的 `Question`，對應 `"Q<no>"`。
- **題組：** `QuestionGroup`，`question_nos` 是題組內的系統題號，對應 `"G<group_no>"`。
- **顯示所需欄位：** `source_no_display`（原始題號，空白時顯示「（未標示）」）、`sub_label`、`sheet_name`。

目前 app 內沒有「推導單位」的函式，只有測試用的 `tests/results_helpers.py`，建議在 `app/results/` 新增一個。

### 身分與鎖定：`app/security.py`、`app/state.py`

- **視窗識別：** `WindowRegistry` 負責發視窗 ID，以及以視窗為單位的失敗鎖定：`lock_remaining`、`record_failure`、`record_success`。老師登入就是這樣用的，見 `app/api/teacher.py`。輸入代碼可以沿用同一套。
- **學生 Token：** 用 `SessionStore.issue("group", window_id, group_id=..., activity_id=...)` 發。權限測試已經用 role `"group"` 加上 `group_id` 模擬學生，請沿用這個命名。
- **重新產生代碼：** 用 `revoke_where(lambda s: s.attrs.get("group_id") == gid)` 讓舊 Token 失效，同時要關閉該組的 WebSocket 連線。
- **權限依賴：** `current_session` 與 `require_teacher` 是 FastAPI 依賴。本 change 要新增 `require_group`。注意 Token 無效時，`current_session` 會丟出「登入已失效，請重新登入」。
- **前端：** `app/static/js/api.js` 已處理視窗 ID 與 Token 的 sessionStorage（鍵名 `buzzer.windowId`、`buzzer.token`、`buzzer.role`），以及 Bearer header。

### 錯誤、設定與資料庫

- **錯誤：** 用 `app/errors.py` 的 `AppError(status, code, message, details=..., headers=..., extra=...)`，回應格式統一為 `{"error": {"code", "message", "details"?}}`。
  - 已有的輔助函式：`forbidden()`（無權限執行此操作）、`session_expired()`、`not_found()`。

- **設定：** `app/config.py` 的 `Settings` 以 `BUZZER_` 為前綴。
  - 要新增：答案長度上限、N、K、冷卻開關、組數上限、組名長度。
  - 新設定要同步更新 `.env.example` 與 README 的設定表。`tests/test_integration.py` 會檢查 `.env.example` 的內容。
- **資料庫：** `app/db.py` 目前是 `SCHEMA_VERSION = 3`（第 3 版新增 `worksheet_previews`）。本 change 升到第 4 版。

  - `tests/test_db.py` 要一起更新。

### 啟動與頁面

- **`app/main.py`：** 新的 router 與 WebSocket 端點在這裡註冊。啟動時要把未結束的活動標為「已中斷」。
- **鎖的選擇：** 現有端點都是同步的 `def`，在執行緒池中執行，現有模組用的是 `threading` 的鎖。WebSocket 是 async，所以搶答狀態的那把鎖要在 design 中決定：
  - 讓活動相關端點全部改成 async，並用一把 `asyncio.Lock`。
  - 或者用 `threading.Lock`，但持有期間不可 `await`。
- **老師頁：** `app/static/teacher.html` 與 `teacher.js` 目前有三塊：Google 授權、匯入、已確認的學習單。本 change 要加入：
  - 建立活動、代碼顯示、階段切換
  - 即時監看、判定無效
  - 結果檢視，以及「寫回答案」「下載 CSV」兩個按鈕。後端端點 `POST /api/activities/{id}/writeback` 與 `GET /api/activities/{id}/results.csv` 已經有了，下載可以用 `api.js` 的 `saveResponse`。
- **學生頁：** `app/static/index.html` 目前寫著「學生加入搶答的功能將在下一階段提供」，要換成輸入代碼並進入組別畫面。

### 測試
